# Interpretation Protocol for Project Director Input

Before substantial exploratory input becomes project work, perform a lightweight interpretation pass.

## Extract only categories that actually apply

- **Durable intent** — appears to express enduring project purpose or principle.
- **Requested outcome** — what the director wants investigated, produced, changed, or decided now.
- **Possible requirement** — candidate constraint not yet necessarily accepted.
- **Illustrative example / analogy** — explanatory unless explicitly promoted.
- **Speculative idea / design hypothesis** — worth exploring, not binding.
- **Historical claim needing verification** — requires evidence before use.
- **Temporary assumption** — necessary placeholder; record if materially consequential.
- **Decision candidate** — a consequential choice that may now need proposal/approval.
- **Unresolved issue** — should remain open until relevance and evidence justify resolution.

Do not force every message into every category.

## Ambiguity rule

If it is genuinely unclear whether a statement is illustrative or binding, default to **non-binding**. Surface the ambiguity only when resolving it becomes consequential.

Do not interrupt the director for every small ambiguity. Use judgment for local, reversible matters. Escalate ambiguity when it could change project identity, historical interpretation, major simulation behavior, or architecture.

## Output discipline

When interpretation affects work, preserve the distinction in the relevant artifact. Do not silently rewrite conversational language into an accepted requirement or decision.
